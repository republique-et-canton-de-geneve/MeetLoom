# Security reviews

## gstack `/cso` audit — September 24, 2026

Static audit of `main` after the 0.1.0 release, run through gstack's trusted `gstack-cso` helper (run `1790287748536-5fcffa3aed64615c`, status **partial**: its qualified scanners and runtime reproduction need a Docker socket, unavailable in this environment). Challenge was sequential (no independent reviewer agent). Assessed: application model, attack surface, CI/CD, infrastructure; partially: secrets, dependencies, integrations, LLM/MCP, OWASP, STRIDE, data classification.

| ID / severity                      | Finding                                                                                                                                                                                                                      | Fix and evidence                                                                                                                                                                                                                                                |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `3bea3343` medium, high confidence | Anonymous holders of a form or visitor link could grow the database shared by every session without bound: public writes were limited only per IP (about 3 GB a day of form images from one address against a 5 GiB volume). | Per-publication quotas (5,000 responses, 100 MiB of answers and images, running totals freed by deletions) and 2,000 visitor comments per link, checked under the row lock that serializes submissions. `tests/public-quotas.test.ts` on SQLite and PostgreSQL. |
| `69baa7ed` low, high confidence    | The 7 MB JSON parser of `/api/import/extract` ran before authentication.                                                                                                                                                     | The session cookie is resolved first and anonymous callers are refused before the body is read. `tests/document-api.test.ts` sends a malformed 2 MB body and expects 401, not 400.                                                                              |

Hardening done in the same pass, without a reported vulnerability: CSP restricted to `'self'` for fonts and styles; per-account API budget (a room of visitors behind one address was throttled, found by the load test); audit trail of administrator actions; lint and dead-code gates. Accepted risks and remaining checks are listed in [architecture-review.md](architecture-review.md).

## Targeted security review — September 23, 2026

Review of the `codex/meetloom-v1` working code using the Gstack checklist: SQL and transactions, concurrency, authorization, AI/MCP output boundaries, public fields, tokens, and errors. The reviewed scope covered `accounts`, `oidc`, `mailer`, `participants`, `transfers`, `sharing`, `mcp`, and their mounting points. Existing security tests were read as evidence of safeguards, without sending anything to an external service.

This document is neither a security certificate nor a complete PR review. New files were still untracked during the preamble, other agents were continuing their changes, and the external Claude review CLI was not installed. No deployment, real OIDC provider, or real SMTP server was used.

## Reproduced and fixed defects

| Severity / confidence | Trigger and consequence before the fix                                                                                                                                          | Fix and evidence                                                                                                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1 / 10 out of 10     | A recovery link issued before an email or password change remained usable.                                                                                                      | Recovery tokens are deleted in the transaction that changes those credentials. `accounts.test.ts` verifies rejection of the previous link in both cases.                                                                            |
| P1 / 10 out of 10     | An in-flight profile save carrying the old email without password confirmation could restore that address after a concurrent legitimate change.                                 | CAS on the email and password hash that were read, and rejection of disabled accounts. A test explicitly controls the interleaving of both requests.                                                                                |
| P1 / 10 out of 10     | Account deletion that had read old credentials could continue after concurrent account recovery.                                                                                | Account lock and re-reading the hash and administrator/active status inside the transaction. Recovery between reading and deletion returns `ACCOUNT_CHANGED` and preserves the account.                                             |
| P1 / 10 out of 10     | A copy/transfer prepared before access revocation could still write afterward because only the source version was checked again.                                                | Re-read the active account, source/destination access, and lifecycle under session locks. Tests revoke source and destination access before writing: the destination remains unchanged.                                             |
| P1 / 10 out of 10     | An MCP grant without internal-data access prohibited certain block fields but still allowed overwriting the general description or deleting a subtree containing internal text. | Consistent validation of targeted operations and deleted descendant content. The SDK client test rejects these writes and verifies that data remains intact. Creation with content supplied entirely by the client remains allowed. |
| P1 / 10 out of 10     | The connector without a private-data grant reused the visitor projection, which intentionally includes the general session description.                                         | A more restrictive MCP projection: empty description without the private-data grant, actual description with it. Sentinel test. Visitor links retain their documented general context.                                              |
| P2 / 10 out of 10     | Reissuing an invitation after ownership transfer retained the previous creator, so acceptance was always refused.                                                               | The upsert updates the authorized creator without changing the identifier assigned to blocks. Test with an actual ownership transfer: the old link is refused and the new link accepted.                                            |

After the same concurrency pattern was reported, the sharing module owner added authorization rechecks to mutations of links and visitor comments. Sharing/lifecycle tests ran separately. The private-comments panel now presents closed sessions as read-only; drafts are hidden and retained, and server-side mutations remain refused.

## Checks run after the fixes

`tests/accounts.test.ts`, `services.test.ts`, `participants.test.ts`, `mcp.test.ts`, and `transfers.test.ts`: **29 tests passed on SQLite and 29 on local PostgreSQL**. PostgreSQL uses separate test schemas removed by the harness. OIDC and SMTP transports are mocked; the MCP test uses the real HTTP SDK client against the local application. The complete project suite is a separate check to rerun once the ongoing UI/export work stabilizes.

Additional evidence covers expired/revoked invitations and the absence of automatic administrator creation, state/nonce/PKCE and verified OIDC email, disabled accounts, non-enumerating recovery, absence of raw tokens in the database, private/public audiences, and expired/revoked MCP grants. These tests do not cover the PowerPoint overlay, real internal providers, OpenShift configuration, or cross-browser acceptance.

The subsequent image-form and folder work passed **16/16 on SQLite and 16/16 on PostgreSQL** across `form-images.test.ts`, `accounts.test.ts`, `content-api.test.ts`, and `form-ai.test.ts`. Coverage includes private image access, per-image/per-response limits, idempotency, cascading deletion, exclusion of binaries from AI and CSV, and deletion of personal folders during account deletion. Later Chrome testing confirmed real PNG selection, preview, submission, and authenticated response-image viewing; see [manual-qa.md](manual-qa.md).

## Limits to retain

- (September 23) One application replica was planned then. Since September 24, two pods run with presence in PostgreSQL and a startup schema lock; rate-limit counters remain per pod.
- The added transfer and sharing checks re-read permissions inside their transaction. This is not a formal proof that every endpoint's authorization is linearizable against every simultaneous revocation.
- SMTP reminders require opt-in and recheck recipient/access before building the message. SMTP acceptance followed by a crash before recording success can cause repeated delivery; exactly-once delivery is not promised.
- The MCP connector uses explicit personal tokens; no OAuth discovery/DCR, publication, participant identity access, or form-response access through MCP tools.
- Functional parity and user acceptance remain tracked in [product-parity.md](product-parity.md), independently of the security review.
